# netdata

Один парент (russia-03) и дети, которые стримят ему свои чарты. Парент считает
тревоги и рассылает уведомления; конфиги правил перечисляются в
`netdata_health_files`, джобы сборщиков — в `netdata_httpcheck_jobs`,
`netdata_filecheck_files`, `netdata_ping_jobs`, `netdata_prometheus_jobs`.

Имена джоб load-bearing: правила в `files/netdata/health.d/*.conf` цепляются за
них через `chart labels: _collect_job=...`. Переименовал джобу — почини правило,
иначе тревога молча перестанет существовать.

## Соглашения, действующие для всех правил

Эти вещи повторяются почти в каждом конфиге, поэтому записаны здесь, а не в
каждом файле по отдельности.

**Правила живут только у парента.** Он считает шаблоны и по стримящимся детским
чартам тоже, так что одно и то же правило, задеплоенное с обеих сторон, даст два
уведомления на одно событие. Исключение — `fleet-watch.conf` и
`fleet-uplink.conf`: они специально стоят на finland-01, чтобы сработать, когда
умер сам парент или линк до него. Ради этого у них отдельные префиксы джоб
(`watch_*`, `uplink_*`) — общий префикс вернул бы двойные уведомления.

**Уведомляет только парент.** У детей дефолтный Telegram выключен
(`health_alarm_notify.conf.j2`), открыты лишь `fleetcrit` и `link` — роли
правил выше. Отвалившийся стрим ловит `fleet_streaming_lost` у парента.

**httpcheck-правило — `average -2m unaligned of success`, `crit: $this < 0.5`.**
Полное падение ловится за ~минуту, как прежний `max -1m`, а флап «каждый
второй запрос» — тоже. Пробам с `every: 1m` окно 5m. Стоковые httpcheck-алерты
у парента заглушены (`httpcheck-stock-off.conf`), так что новая джоба без
своего правила остаётся без алерта.

**httpcheck-пробы — в infra, алерты на метрики приложения — в его репо.** Проба
`/health` одинакова у всех и живёт по соглашениям выше; правило на prometheus-
метрику привязано к имени из кода и меняется в одном PR с ним
(`ops/netdata/health.d` приложения, `remote: true` в `netdata_health_files`).

**Алерт, родившийся в CRITICAL, netdata сообщает ненадёжно** (после старта
агента и переподключения ребёнка — то уходит, то нет; так 14–16.10 молча
пролежал API Директа). Дыру закрывает `unnotified-alarms` у парента: раз в
2 минуты досылает в Telegram CRITICAL, по которым за эпизод не запускался
alarm-notify. Только Telegram — Pushover такой алерт не поднимет.

**`delay: up 5m` у проб, зависящих от RF↔EU.** Всё, что ходит к базе на
finland-01 или едет по wg, поднимается разом при флапе линка. Причину без
задержки приносит `link_host_unreachable`; остальные ждут пять минут, чтобы
телефон звонил на настоящей аварии, а не на тридцати секундах потерь.

**Контекст filecheck сверен с живым агентом** (2026-09-07):
`filecheck.file_modification_time_ago` / `mtime_ago`. Первая догадка по докам не
совпала ни с одним чартом, и тревога молча не срабатывала. После мажорного
апгрейда netdata проверить заново:
`curl -s localhost:19999/api/v1/charts | grep filecheck`.

## Чаты проектов

Кроме чата владельца, алерты о простое проекта могут приходить в чат его
разработки. Источник правды — реестр: у приложения в `apps.yml` поле
`alert_chats` (chat id или `chat:thread` для топика). Роль на паренте выводит
из реестра `/etc/netdata/alarm-telegram-routes.json` (0640 root:netdata):
чаты, pm2-процессы, префикс имён (`val-id` → `val_id`), `netdata_projects_required`
и URL httpcheck-проб проекта. Реестр общий, поэтому в файл попадают все
приложения с `alert_chats`, на каком бы хосте они ни жили: алармы всех нод
считает и рассылает парент.

`alarm-telegram` после обычной отправки владельцу определяет проект аларма
(`files/alarmroutes.py`, как `project_of` страницы статуса: pm2-чарт
`app.pm2_<процесс>_processes`, файл health.d из `src`, префикс имени аларма
или джобы пробы) и, если это аларм простоя, шлёт то же событие в чаты проекта.

- Аларм простоя: `pm2_app_down`, `mysql_down`, `clickhouse_down`, `*_health_down`,
  `*_healthcheck` (REQUIRED страницы статуса) и `netdata_projects_required[<проект>]`.
  Метрические алармы (ошибки ЧЗ, упавшие выгрузки) идут только владельцу.
- В чат проекта — только CRITICAL и его закрытие: «🔴 val-id недоступен —
  процесс val-id-api не запущен» / «— не отвечает https://val-id.ru/healthz»,
  «🕒 Началось: … МСК»; CLEAR редактирует то же сообщение: «✅ val-id снова
  работает», «✅ Восстановлено», «⏱ Длилось». Без ноды, чарта и ссылки на
  netdata. Эпизод у каждого чата свой.
- Сбой чата проекта виден только в журнале alarm-notify и на код возврата не
  влияет; провал всех чатов владельца — по-прежнему ошибка.
- `unnotified-alarms` досылает пропущенные CRITICAL только владельцу.

### Подключить чат проекта

1. Добавить бота алертов (@GistrecCloudBot) в чат проекта: в privacy mode ему
   достаточно команд.
2. Написать в чате `/id` (в нужном топике, если алерты должны идти туда) —
   бот ответит значением для `alert_chats`, например `-1001234567890` или
   `-1001234567890:42`.
3. Вписать его в `apps.yml` у приложения: `alert_chats: ["-1001234567890"]`
   (в кавычках). Если у проекта нет `*_health_down`, добавить httpcheck-пробу и
   аларм, иначе в чат придёт только падение pm2-процесса.
4. Прогнать роль на паренте: `ansible-playbook site.yml -l russia-03 --tags netdata`.
5. Проверить в чате: `/alerts` — какие проверки сюда приходят, `/status` — их
   состояние (через минуту, когда status-snapshot перепишет alert-feed.json).

## Данные для команд бота

Команды `/id`, `/alerts`, `/status` живут не здесь, а в приложении бота
(`gistrec-cloud-bot` на finland-01, репозиторий GistrecCloudBot): у этого токена
уже есть свой getUpdates, второй слушатель конфликтовал бы с ним. Отсюда бот
берёт данные: при `netdata_alert_feed_dir` status-snapshot раз в минуту пишет
туда `alert-feed.json` (отдельный каталог: каталог страницы статуса закрыт
авторизацией stats-vhost):

- `owner_chats` — чат владельца (`netdata_telegram_chat_id`);
- `chats` — по проекту с `alert_chats`: его чаты и проверки простоя уже
  человеческими словами («процесс val-id-api», «ответ https://val-id.ru/healthz»)
  со статусом и временем начала;
- `projects` — проекты страницы статуса (вид, худший статус, outage) и их
  алармы: имя, статус, с какого времени.

Токена, нод, чартов и ссылок в файле нет. Отдаёт его nginx парента в
`health.conf` (`location = /alert-feed.json`) только адресам из
`nginx_alert_feed_allow` — wg-IP finland-01; запрос с любого другого адреса,
в том числе с подставленным Host, получает 403. Бот читает
`http://<wg-IP парента>/alert-feed.json`, тем же путём, что NETDATA_URL.

Тесты скриптов: `python3 -m unittest discover -s ansible/roles/netdata/tests -v`
(без сети; в CI — джоба `python tests`).
