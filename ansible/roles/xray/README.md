# xray

Один VLESS-inbound с XTLS-Reality на хосте. Роль опциональна
(`xray_managed`), ставит пиновый бинарь из релизов XTLS и держит конфиг
шаблоном — ничего, кроме этого inbound, она не настраивает.

Все значения, которые делают inbound рабочим (ключ, клиентские id, порт,
`dest`/`serverNames`), — свойства машины, а не парковый код: они живут в
гитигнорных host_vars и в vault. Дефолты роли пустые, и без них она падает
на assert'ах, а не поднимает что-то наугад.

## Почему Reality, а не TLS с собственным сертификатом

Обычный TLS-inbound требует домена, сертификата и A-записи — то есть трёх
артефактов, которые придётся заводить и продлевать. Reality вместо этого
отдаёт рукопожатие внешнего сайта (`dest`) всем, кто не предъявил
`shortIds`, и его сертификат видит клиент. Своей DNS-записи схема не
требует вообще, и сертификат продлевать нечего.

Цена — выбор `dest`: сайт должен уметь TLS 1.3 и h2 и быть доступен с хоста.
Домен из `serverNames` подставляется клиентом в SNI, так что он должен
совпадать с тем, что реально отдаёт `dest`.

## Порт

Дефолт `xray_port: 443` — то, чего ждёт TLS-клиент. Роль не угадывает, кто
ещё слушает хост: если 443 занят (nginx), порт задаётся в host_vars, и там же
его надо открыть в `firewall_extra_open_tcp_ports` — иначе inbound окажется
за default-drop цепочкой, а снаружи это выглядит ровно как блокировка у
провайдера. Роль проверяет это assert'ом.

## Что закрыто для клиентов

`xray_blocked_cidrs` отправляет петлю, link-local и приватные диапазоны в
blackhole. Это не гигиена ради гигиены: на том же хосте живут MySQL,
ClickHouse и меш wg0 — без этого правила клиент дотянулся бы до `10.10.0.0/24`
и до сервисов на `127.0.0.1`, минуя firewall хоста.

Чтобы правило ловило не только запрос голого адреса, но и домен, который в
приватный адрес разрешается, в `routing` стоит `domainStrategy: IPIfNonMatch`
— xray резолвит имя до сопоставления правил. Платим одним DNS-запросом на
новое соединение.

`xray_block_smtp` глушит исходящий 25: порт, из-за которого от хостера
приходит abuse, а узнаёшь об этом последним.

## Проверка конфига

Задача с шаблоном вызывает `xray run -test`, прежде чем положить файл на
место. Без этого xray стартует, молча проигнорировав неизвестный ключ
(переименованное поле `realitySettings` — живой случай), и диагноз сводится к
«клиент не подключается» без единой строки в журнале.

## Переменные

| переменная | смысл |
|---|---|
| `xray_managed` | включает роль (по умолчанию `false`) |
| `xray_version`, `xray_archive_sha256` | пин релиза — без него пересборка хоста поставила бы другую сборку; sha256 берётся из `.dgst` рядом с архивом |
| `xray_loglevel` | уровень журнала самого сервиса (`warning`) |
| `xray_access_log` | `none` выключает; `""` включает запись в journald — см. «Отладка» |
| `xray_listen`, `xray_port` | адрес и порт inbound |
| `xray_reality_enabled` | поднимать VLESS-inbound (по умолчанию да) |
| `xray_clients` | `[{name, uuid}]`; uuid и есть пароль — только из vault |
| `xray_reality_dest` | `host:port` внешнего сайта для рукопожатия |
| `xray_reality_server_names` | список SNI, которые принимает inbound |
| `xray_reality_private_key` | приватный x25519 — из vault |
| `xray_reality_short_ids` | список hex-строк, вторая половина пароля — из vault |
| `xray_relay_enabled` | поднимать реле (по умолчанию нет) |
| `xray_relay_port` | порт реле; по умолчанию равен `xray_port` |
| `xray_relay_target_address`, `xray_relay_target_port` | куда переливать; адрес задавать в меше, порт по умолчанию 443 — тогда в клиентском профиле отличается только адрес сервера |
| `xray_blocked_cidrs` | что клиентам недоступно |
| `xray_block_smtp` | глушить исходящий 25 |
| `xray_freedom_strategy` | семейство адресов для исходящих; `UseIPv4` предсказуемее, и капчу на дата-центровые `/64` раздают охотнее, чем на IPv4 |

## Генерация материала

```bash
xray x25519                 # privateKey + публичный ключ для клиента
openssl rand -hex 8         # shortId
uuidgen                     # id клиента, по одному на устройство
```

Публичный ключ в конфиге сервера не нужен — он нужен только клиенту, поэтому
роль его и не хранит. Держать его рядом с остальным материалом всё равно
стоит: по приватному ключу он восстанавливается, но не теми командами, что
под рукой.

## Реле

`xray_relay_enabled` поднимает второй инбаунд — `dokodemo-door`, который
переливает TCP на `xray_relay_target_address` и ничего в нём не разбирает.
Нужно, когда клиенту выгоднее постучаться на ближний хост, а выходить через
дальний.

Ключевое свойство: рукопожатие Reality терминируется на **дальнем** хосте.
Поэтому реле не нужны ни ключи, ни список клиентов (`xray_reality_enabled:
false`), а в клиентском профиле меняется только адрес сервера — SNI, публичный
ключ, shortId и uuid остаются от дальнего хоста.

Цель задаётся адресом в меше, тогда межсерверный участок едет по wg и не
добавляет публичной поверхности.

Две кромки, на которые роль рассчитывает:

- **На реле нет `sniffing`.** С ним xray подменил бы адрес назначения на имя
  из SNI, и байты перестали бы попадать в цель.
- **Правило реле идёт первым в `routing`.** Цель лежит в меше, то есть внутри
  `10.0.0.0/8` из `xray_blocked_cidrs`; без этого порядка реле уходило бы в
  blackhole.

Чего реле стоит: дальний хост видит все соединения с адреса ближнего, так что
различение устройств в журнале доступа теряется.

## Отладка «подключился, но страница не грузится»

Порядок такой, потому что первый шаг делит задачу пополам: до сервера или
после.

1. **Дошло ли соединение.** Поставить `xray_access_log: ""` в host_vars,
   прогнать роль, смотреть `journalctl -u xray -f`. Записи `accepted …
   [vless-reality >> direct] email: <клиент>` означают, что рукопожатие,
   Reality и аутентификация в порядке — дальше виноват путь или цель. Пусто
   значит обратное: клиент, порт или DPI. **Вернуть `none` после отладки**:
   журнал пишет каждый адрес назначения, то есть всю историю посещений.
2. **Качество пути.** `ss -tin | grep <адрес клиента>` и смотреть `retrans`,
   `rto`, непустую `Send-Q`. `rto:120000` = соединение дошло до максимального
   таймаута и фактически стоит; `Send-Q` у всех сокетов подряд = данные не
   забираются клиентом, то есть потери, а не нагрузка.
3. **MTU.** Мерить `ping -M do` до клиента обычно бессмысленно — ICMP режут и
   провайдер, и NAT. Дешевле не измерять, а понизить MTU на клиенте (у
   sing-box по умолчанию 9000, разумное значение 1380). Симптом как раз
   такой: рукопожатие мелкими пакетами проходит, первый крупный ответ встаёт.
4. **Достаёт ли цель сам сервер.** `curl -4 -o /dev/null -w '%{http_code}'` с
   хоста. Осторожно с выводом: 403 у curl сам по себе не значит, что адрес
   забанен. Если в ответе `cf-mitigated: challenge` и `<title>Just a
   moment...</title>` — это интерактивный челлендж Cloudflare, который curl
   не умеет решать, а браузер проходит. Банами с дата-центровых адресов
   грешат AI-сервисы, и отличить бан от челленджа можно только по этому
   заголовку.
5. **Не включён ли второй VPN.** Вложенный тоннель (чужой OpenVPN внутри
   этого) даёт двойную инкапсуляцию и схлопывает MTU. В журнале доступа
   видно сразу: соединения на нетипичный UDP-порт чужого сервиса.

## Клиентский профиль

Роль настраивает только серверную сторону. Маршрутизация — какие домены идут
в тоннель, а какие напрямую — целиком клиентская и в этой роли не живёт.
