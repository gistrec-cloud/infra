# k3s

Одноузловой Kubernetes (k3s) там, где хост делится с чужим сервисом. Роль
опциональна (`k3s_managed`), сегодня её включает только germany-02.

## Почему сокет остаётся на 0.0.0.0

Хочется поставить `--bind-address` на свой адрес и закрыть вопрос, но у k3s на
этом же порту сидит супервизор, к которому ходят локальные компоненты. Сузив
bind, легко получить узел, который не может достучаться до собственного
apiserver, — отладка дорогая, выигрыш нулевой.

Поэтому ограничение живёт в ufw. Предпочтительный вариант — `k3s_api_allow_interface`:

```
ufw allow in on <меш-интерфейс> to any port 6443 proto tcp
```

Снаружи порт тогда закрыт полностью, а адрес источника не важен. Это не
теоретическое удобство: allow-лист по домашнему адресу протух за сутки
(динамический IP уехал), и kubectl перестал ходить в тот же день, когда
кластер подняли.

Вариант по адресам (`k3s_api_allow_from`) остался для случаев без меша; `dest`
там пинит `k3s_node_ip`, так что на других адресах хоста порт закрыт. Модуль ufw
состояние не сверяет, поэтому отзыв доступа — отдельным списком
`k3s_api_revoke_from`, иначе снятое из allow-листа правило останется на хосте.

`node-ip` и `node-external-ip` указывают на `k3s_node_ip` — наружу узел
представляется одним адресом. А вот **сертификат одним адресом не обойдётся**:
`tls-san` строится из `k3s_node_ip`, то есть из ПУБЛИЧНОГО адреса, и клиент,
пришедший по адресу меша, упрётся в несовпадение имени. Адрес в меше надо
добавить в `k3s_tls_san_extra` явно, иначе единственный путь, который пускает
ufw, не проходит проверку сертификата.

kubeconfig с хоста указывает на `127.0.0.1` и правки не требует.

**Добавили SAN уже работающему кластеру — проверьте, что он доехал.** Публичный
порт обслуживает dynamiclistener, который кэширует сертификат в
`/var/lib/rancher/k3s/server/tls/dynamic-cert.json` и в секрете `k3s-serving`;
одного рестарта может не хватить. Сверять фактом, а не отчётом ansible:

```bash
openssl s_client -connect 127.0.0.1:6443 </dev/null 2>/dev/null \
  | openssl x509 -noout -ext subjectAltName
```

Если нового имени нет — удалить `dynamic-cert.json` и секрет
`kube-system/k3s-serving`, затем перезапустить k3s.

kubelet (10250) слушает только на `k3s_node_ip` и никаких allow-правил не
получает.

## Соседство на общем хосте

Роль исходит из того, что хост не наш целиком, и трогает минимум:

- **ufw не переписывается.** Дефолтные `deny incoming` и `FORWARD DROP`
  остаются; добавляются только два `route allow` для подсети подов и по одному
  allow на оператора. Без route-правил flannel дописал бы ACCEPT в конец
  FORWARD, а первый же `ufw reload` их снёс бы — сломав наши поды.
- **swap не выключается.** Вместо `swapoff`, который задел бы чужую нагрузку,
  kubelet получает `fail-swap-on=false`.
- **traefik и servicelb отключены.** Иначе traefik занял бы 80/443, а servicelb
  раздавал бы порты на всех адресах, включая соседский.
- **Подсети проверяются перед установкой.** Роль падает, если `cluster-cidr`
  или `service-cidr` пересекается с уже существующим маршрутом.

Чего роль НЕ делает: не включает `ip_forward` (проверьте, что он уже `1`) и не
управляет ufw за пределами своих правил.

## Переменные

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `k3s_managed` | `false` | Включает роль на хосте |
| `k3s_node_ip` | — | Обязательна: `node-ip`, первый SAN, `dest` для ufw. Публичный адрес узла |
| `k3s_api_allow_interface` | `""` | Интерфейс, с которого API открыт без учёта адреса источника — меш |
| `k3s_api_allow_from` | `[]` | Публичные адреса, которым открыт API. Пусто = наружу не открыт |
| `k3s_api_revoke_from` | `[]` | Адреса, у которых доступ снимается (ufw не сверяет состояние сам) |
| `k3s_tls_san_extra` | `[]` | Доп. имена в сертификате API. **Адрес узла в меше — сюда**, из `k3s_node_ip` он не выводится |
| `k3s_version` | `""` | Версия при установке с нуля. Апгрейдом НЕ управляет — см. ниже |
| `k3s_cluster_cidr` / `k3s_service_cidr` | `10.42.0.0/16` / `10.43.0.0/16` | Проверяются на пересечение с маршрутами |
| `k3s_disable` | `[traefik, servicelb]` | Компоненты, которые заняли бы чужие порты |

## kubectl с ноутбука

Когда API открыт только в меше (`k3s_api_allow_interface`), ноутбук до него не
достаёт — в сетку он не входит. Нужны две РАЗНЫЕ машины: сам узел кластера, где
лежит kubeconfig, и любой узел меша как точка входа.

```bash
# kubeconfig есть ТОЛЬКО на узле с k3s — не на произвольном узле меша
ssh <k3s-узел> sudo cat /etc/rancher/k3s/k3s.yaml > ~/.kube/k3s.yaml
# проброс — через любой узел меша, к адресу k3s-узла В МЕШЕ (wireguard_ip)
ssh -o ExitOnForwardFailure=yes -f -N -L 6443:<wireguard_ip узла k3s>:6443 <любой-узел-меша>
KUBECONFIG=~/.kube/k3s.yaml kubectl get nodes
```

Перенаправление `>` выполняется локально, поэтому `ssh` не к тому хосту сначала
обнулит `~/.kube/k3s.yaml`, а потом сообщит, что файла нет.

`ExitOnForwardFailure` обязателен: без него занятый локальный 6443 не помешает
`ssh` запуститься, и kubectl с админским сертификатом уйдёт к чужому слушателю.

Конфиг с хоста уже указывает на `https://127.0.0.1:6443`, править его не нужно.

## Апгрейд и снос

Апгрейд ролью НЕ делается: у таска установки стоит `creates:`, поэтому на хосте
с уже стоящим бинарём он пропускается, а `k3s_version` никуда не доезжает —
прогон покажет зелёное и ноль изменений при старой версии. Апгрейд руками:
`curl -sfL https://get.k3s.io | INSTALL_K3S_VERSION=<версия> sh -` на хосте,
затем зафиксировать версию в `k3s_version`, чтобы следующая установка с нуля
воспроизвела ту же.
Снос — `/usr/local/bin/k3s-uninstall.sh` на хосте: он убирает юнит, containerd,
интерфейсы `cni0`/`flannel.1` и правила kube-proxy. Правила ufw, заведённые
ролью, он не знает — снимать вручную (`ufw status numbered` → `ufw delete <N>`).
