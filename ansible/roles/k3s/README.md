# k3s

Одноузловой Kubernetes (k3s) там, где хост делится с чужим сервисом. Роль
опциональна (`k3s_managed`), сегодня её включает только germany-02.

## Почему сокет остаётся на 0.0.0.0

Хочется поставить `--bind-address` на свой адрес и закрыть вопрос, но у k3s на
этом же порту сидит супервизор, к которому ходят локальные компоненты. Сузив
bind, легко получить узел, который не может достучаться до собственного
apiserver, — отладка дорогая, выигрыш нулевой.

Поэтому ограничение живёт в ufw. Предпочтительный вариант — `k3s_api_allow_interface`:

```
ufw allow in on <меш-интерфейс> to any port 6443 proto tcp
```

Снаружи порт тогда закрыт полностью, а адрес источника не важен. Это не
теоретическое удобство: allow-лист по домашнему адресу протух за сутки
(динамический IP уехал), и kubectl перестал ходить в тот же день, когда
кластер подняли.

Вариант по адресам (`k3s_api_allow_from`) остался для случаев без меша; `dest`
там пинит `k3s_node_ip`, так что на других адресах хоста порт закрыт. Модуль ufw
состояние не сверяет, поэтому отзыв доступа — отдельным списком
`k3s_api_revoke_from`, иначе снятое из allow-листа правило останется на хосте.

Сертификат, kubeconfig и `node-ip` указывают на `k3s_node_ip` — наружу узел
представляется одним адресом. kubelet (10250) слушает только на нём и никаких
allow-правил не получает.

## Соседство на общем хосте

Роль исходит из того, что хост не наш целиком, и трогает минимум:

- **ufw не переписывается.** Дефолтные `deny incoming` и `FORWARD DROP`
  остаются; добавляются только два `route allow` для подсети подов и по одному
  allow на оператора. Без route-правил flannel дописал бы ACCEPT в конец
  FORWARD, а первый же `ufw reload` их снёс бы — сломав наши поды.
- **swap не выключается.** Вместо `swapoff`, который задел бы чужую нагрузку,
  kubelet получает `fail-swap-on=false`.
- **traefik и servicelb отключены.** Иначе traefik занял бы 80/443, а servicelb
  раздавал бы порты на всех адресах, включая соседский.
- **Подсети проверяются перед установкой.** Роль падает, если `cluster-cidr`
  или `service-cidr` пересекается с уже существующим маршрутом.

Чего роль НЕ делает: не включает `ip_forward` (проверьте, что он уже `1`) и не
управляет ufw за пределами своих правил.

## Переменные

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `k3s_managed` | `false` | Включает роль на хосте |
| `k3s_node_ip` | — | Обязательна: SAN сертификата, endpoint kubeconfig, `dest` для ufw |
| `k3s_api_allow_interface` | `""` | Интерфейс, с которого API открыт без учёта адреса источника — меш |
| `k3s_api_allow_from` | `[]` | Публичные адреса, которым открыт API. Пусто = наружу не открыт |
| `k3s_api_revoke_from` | `[]` | Адреса, у которых доступ снимается (ufw не сверяет состояние сам) |
| `k3s_version` | `""` | Пусто = stable на момент установки; задать для воспроизводимого апгрейда |
| `k3s_cluster_cidr` / `k3s_service_cidr` | `10.42.0.0/16` / `10.43.0.0/16` | Проверяются на пересечение с маршрутами |
| `k3s_disable` | `[traefik, servicelb]` | Компоненты, которые заняли бы чужие порты |

## kubectl с ноутбука

```bash
ssh <host> sudo cat /etc/rancher/k3s/k3s.yaml > ~/.kube/germany-02.yaml
sed -i '' "s#https://127.0.0.1:6443#https://<k3s_node_ip>:6443#" ~/.kube/germany-02.yaml
KUBECONFIG=~/.kube/germany-02.yaml kubectl get nodes
```

Файл содержит клиентский сертификат администратора — обращаться как с паролем.

## Апгрейд и снос

Апгрейд — задать `k3s_version` и прогнать роль; установщик перезапишет бинарь.
Снос — `/usr/local/bin/k3s-uninstall.sh` на хосте: он убирает юнит, containerd,
интерфейсы `cni0`/`flannel.1` и правила kube-proxy. Правила ufw, заведённые
ролью, он не знает — снимать вручную (`ufw status numbered` → `ufw delete <N>`).
